# Participant session recovery

On the participant page, sign in under Commissioner, select the existing player in Restore player access, and generate a recovery code. Confirm the requester's identity and share the code privately. The player opens Already joined? Recover your picks and pastes it there. Codes are not placed in URLs, QR images, browser storage or public read models.

Each code has a cryptographically random 256-bit secret, stored only as a hash, and expires after 15 minutes. A newly issued code replaces the prior code for that participant. Generation alone does not sign the player out. Redemption atomically consumes the code, increments the participant's session generation and issues a normal secure HttpOnly cookie. All older participant sessions fail generation validation. Legacy sessions and participants default to generation zero, so deployment does not sign out existing players.

Recovery preserves the same participant, card revision, submission status, picks and prediction. It works after lock and after finalization, but never bypasses editing or Reveal restrictions. Card transactions also condition on the session generation to reject a stale write prepared before recovery. Issuance and redemption are audited without code secrets. Concurrent redemption permits only one success. If the browser loses the successful response, the commissioner can generate another code.

DynamoDB uses a single expiring RECOVERY record under the contest partition, keyed by participant. Its application expiry check is authoritative; asynchronous TTL deletion is cleanup only. Redemption updates the session generation using a conditional nested update, preserving concurrent card fields. Codes, sessions, and participant updates commit in one transaction with the contest version. No index or new AWS permission is needed. The local adapter provides the same semantics.

Verification: 71 unit/API/repository tests pass; DynamoDB Local exercises atomic concurrent redemption, same-card restoration, old-session rejection, stale-generation writes and recovery after lock. The browser rehearsal restored a synthetic submitted card in MAIN_EVENT with pick controls still disabled. The cloud rehearsal covers recovery before and after lock in a disposable synthetic contest. No external dependencies were added.

Deployment verified: the published frontend matches the build and the real revised contest remains PREGAME with no public picks. The cloud rehearsal passed recovery before/after lock and the full game-day flow, then removed 136 synthetic records. An earlier concurrent-save attempt hit retryable database contention and removed its 109 records; the smoke test now retries 503 responses using the same expected revision. No existing player session was reset by deployment.
